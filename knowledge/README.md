# Сервис документов Process Hub

Универсальная библиотека документов, оригиналов и комплектов редакций внутри Process Hub. Управление ролями и сотрудниками находится в отдельном модуле «Управление доступом». Сервер документов и база отделены от хранения схем. Новый контракт и ограничения: [DOCUMENT_LIBRARY.md](../docs/knowledge/DOCUMENT_LIBRARY.md). Клиент Nova подготовлен; смысловая сверка ещё не реализована.

## Подключение локальной платформы

1. Скопируйте `.env.example` в `.env` в корне репозитория. `.env` исключён из Git.
2. Сгенерируйте `SQB_KNOWLEDGE_SECRET` (не менее 32 случайных символов). Одинаковое значение используется Hub и knowledge только в одном окружении.
3. Задайте отдельный `KNOWLEDGE_DB_PASSWORD`. Пароль примера предназначен для локальной проверки.
4. Запустите из корня:

```sh
docker compose --profile knowledge up -d --build
```

Библиотека доступна на обычном адресе Hub в разделе «Документы». Поддерживаются PDF, DOCX, DOC и XLSX; один комплект до 10 файлов, по 10 МиБ на файл и до 40 МиБ суммарно. База документов и внутренний API не публикуют порты наружу. Без секретного контекста сервис не запускается. Обычный запуск без профиля сохраняет прежнюю платформу; новый раздел сообщает, что сервис не подключён.

При добавлении модуля к работающей платформе нужно пересоздать также `api`, чтобы он получил `SQB_KNOWLEDGE_SECRET` из `.env`. Команда выше выполняет это через изменившуюся конфигурацию. Изменение пароля PostgreSQL в `.env` не меняет пароль уже созданного тома автоматически; используйте штатную процедуру смены пароля БД, не удаляйте том.

## Настройка Nova пользователем

В корневом `.env` заполните:

```dotenv
NOVA_BASE_URL=http://nova-gateway.internal:11450/api/v1/services/rag
NOVA_API_KEY=
NOVA_COLLECTION=
```

Адрес — RAG-сервис Nova Platform (https://nova.example.internal/docs) без `/v1` и без ключа; ключ `nova_…` создаётся на https://nova.example.internal/keys. Имя коллекции должно быть разрешено вашему ключу. Если банк выдал HTTP-адрес, сеть между сервисом и Gateway должна быть разрешена в банковском контуре. Для HTTPS применяется штатная проверка сертификата; она не отключается.

Применение настроек и диагностика:

```sh
docker compose --profile knowledge up -d knowledge
docker compose exec knowledge python -m knowledge_service.cli nova-probe
```

Проверяются доступность Gateway и наличие коллекции; `search_verified`, `model_verified`, `full_source_verified` остаются false. Диагностика не отправляет тексты инструкций. Реальная проверка поиска/модели выполняется следующим этапом на согласованных примерах. Нет автоматических вызовов Nova при запуске или загрузке файла.

Для явной проверки поиска подготовьте согласованный UTF-8 файл запроса внутри контейнера и запустите `python -m knowledge_service.cli nova-check --query-file /path/query.txt`. Опция `--model-check` проверяет ответ модели синтетическим запросом. Отчёт не печатает найденные тексты; качество сверки и полнота положения этой диагностикой не подтверждаются.

## Чтение оригиналов и подготовка функций

Профиль `knowledge` также запускает `knowledge-worker`: оригинал и очередь сохраняются атомарно, обработка выполняется отдельно от HTTP. Worker не получает ключи Nova. По уточнению владельца проекта библиотека должностей показывает полные оригинальные документы; отдельное выделение функций из пользовательского интерфейса убрано. PDF читается непосредственно, DOC/DOCX — через локальную PDF-копию с отдельным исходником. Файлы и редакции не объединяются. Прежние подготовленные источники и API остаются внутренней технической основой и не вызываются для чтения. OCR пока не подключён. Подробный контракт и ограничения: [ROLE_LIBRARY.md](../docs/knowledge/ROLE_LIBRARY.md).

## Внутренний просмотр Word

Профиль knowledge запускает закрытый document-preview: LibreOffice без макросов и обновления ссылок, read-only filesystem, tmpfs и private internal network. В knowledge задан DOCUMENT_PREVIEW_URL=http://document-preview:8000. При отдельном запуске для разработки адрес должен указывать только на доверенный внутренний renderer. При его отсутствии остаётся скачивание исходника. Сервис не получает базу и ключи Nova, не публикует порт. PDF.js и все его ресурсы раздаются самим Hub.

Просмотр страниц требует documents.download на каждом запросе. Выделенные функции доступны с documents.read. Полный контракт: [ROLE_LIBRARY.md](../docs/knowledge/ROLE_LIBRARY.md).

## Департаменты и доступ

Первого главного администратора назначает оператор **в Hub** по точной почте уже зарегистрированного аккаунта. Основание обязательно; назначение не создаёт аккаунт и не меняет пароль:

```sh
docker compose exec api python -m app.admin_cli grant --email ACCOUNT_EMAIL --reason 'Основание назначения'
```

Отзыв — та же команда с `revoke`. Отозвать последнего главного администратора нельзя. Назначение хранится в основной базе Hub и применяется к текущим и будущим департаментам документов через подписанный контекст. Не прописывайте главный аккаунт в исходниках или `.env` для автоматического назначения.

Общая навигация Hub содержит «Библиотеку» (`/`), «Документы департаментов» (`/knowledge`) и «Управление доступом» (`/access`). Административный модуль объединяет «Роли» (`/access/roles`), «Сотрудники» (`/access/employees`) и «Журнал изменений» (`/access/audit`). Прежние `/roles` и `/knowledge/manage` перенаправляют к ролям. Текущая проверка интерфейса выполнена для компьютера.

Департаменты копируются из папок существующего пространства Hub. Ручного создания департаментов нет. На главной модуля показаны папки с исходными названиями, номерами и порядком. Инструкции загружаются внутри выбранной папки без обязательной настройки должностных ролей. Главный администратор использует своё назначение Hub; дублировать его локальными правами Knowledge не нужно.

Оператор выполняет перенос только папок первого уровня внутри выбранного пространства. Команда берёт данные из собственной базы Hub; браузер не передаёт произвольные названия или список папок:

```sh
docker compose exec api python -m app.knowledge_catalog_cli --space-id SPACE_ID --actor-email ADMIN_EMAIL --expected-count 41
```

Число папок проверяется до записи. `catalog_item_id` сохраняет связь с исходной папкой и предотвращает дубли при повторном переносе. Повтор обновляет названия/порядок, сохраняя UUID департамента, инструкции, роли и назначения доступа; отсутствующие в исходном пространстве папки автоматически не удаляются. Перенос является явным операторским действием, не выполняется при каждом чтении экрана. Карты процессов и вложенные папки не копируются в этот реестр.

В разделе «Роли» модуля «Управление доступом» главный администратор создаёт именованную **роль доступа**, выбирает конкретные функции и папки департаментов. Карта включает просмотр, скачивание, регистрацию инструкции, добавление редакций, подготовку текста, удаление и восстановление. Просмотр обязателен, остальные функции независимы; новая роль по умолчанию включает только просмотр и скачивание. Главный администратор имеет все реализованные функции. Разрешена роль без папок: она пока не открывает документы. Область может включать несколько папок; предел API — 500. Названия нормализуются, повторное имя без учёта регистра отклоняется. Для изменения требуются основание и исходный `updated_at`; устаревшая форма получает 409.

Удаление переносит инструкцию в «Удалённые», сохраняя все редакции и оригиналы. Восстановление — отдельная функция; оба действия требуют причины и записываются в неизменяемый аудит. Удалённые документы закрыты для рабочих маршрутов, их незавершённая подготовка отменяется. Прежние `owner`/`reader`/`reviewer` сохранены для совместимости; миграция не предоставляет им удаление. У именованных ролей сервер использует явный массив `capabilities`. Подробная модель: [ACCESS_PLAN.md](../docs/knowledge/ACCESS_PLAN.md).

В разделе «Сотрудники» администратор ищет существующего сотрудника по точной почте, проверяет найденное имя, выбирает созданную роль и указывает основание. Здесь доступны список назначений и отзыв конкретной роли. Пользователю можно назначить несколько ролей. Отзыв одной роли не удаляет другие роли или прежние прямые назначения и не меняет общую сессию Hub либо глобальные административные права.

В отдельном разделе «Журнал изменений» доступны до 100 последних событий управления ролями и назначениями. Поиск и фильтр действуют в этом списке. Неизменяемые записи сохраняют исполнителя, дату, основание и снимки прав; подробности показывают фактическое изменение названия, функций и папок. Журнал помогает установить, кто и почему изменил доступ.

Hub проверяет существование аккаунта перед изменением доступа; браузер не может перечислять пользователей или назначать права несуществующему ID. Проверка прав действует также при прямых API-запросах. Регистрация сама по себе не открывает документы.

**Должностная роль документа** — отдельная необязательная классификация инструкции, например «Главный специалист». Она не назначает доступ сотруднику и не создаётся автоматически при загрузке. Если передан её ID, сервер проверяет принадлежность тому же департаменту; ID роли доступа вместо него не принимается. Служебная CLI для должностных ролей и прежних прямых прав сохранена для совместимости. Используйте только проверенный `id` Hub. Примеры с заменяемыми параметрами:

```sh
docker compose exec knowledge python -m knowledge_service.cli role --department-id DEPARTMENT_UUID --name 'Название роли'
docker compose exec knowledge python -m knowledge_service.cli grant --user-id HUB_USER_ID --department-id DEPARTMENT_UUID --permission owner
```

`reader` видит документы и скачивает оригиналы. `owner` также регистрирует инструкции и загружает версии. `reviewer` пока читает; полномочия рассмотрения будут добавлены вместе со сверкой. Технический доступ к CLI не равнозначен праву утверждать документы. Связь с каталогом создаётся переносом папок, не является кадровым справочником.

Отзыв одного назначения:

```sh
docker compose exec knowledge python -m knowledge_service.cli revoke --user-id HUB_USER_ID --department-id DEPARTMENT_UUID --permission reader
```

Эффективные права — объединение прежних прямых `access_grants` и прав всех назначенных ролей в их папках. Чтобы закрыть весь доступ к папке, уберите все его источники. Изменение области или права роли применяется к её участникам при следующем запросе. Перед записью документа сервер повторно проверяет права после блокировки департамента; завершённый отзыв не обходится ожидающей загрузкой или её повтором. Сохранённая пользователем локальная копия не исчезает после отзыва серверного доступа.

## Загрузка и повтор после сбоя

Внутри департамента выберите «Добавить инструкцию»: единый диалог запрашивает название и оригинал PDF/DOCX до 10 МБ. Должностная роль необязательна; период действия задаётся только если известен. Инструкция, первая редакция и аудит сохраняются одной транзакцией; ошибка файла не оставляет пустую запись. PDF проверяется на структуру и наличие страниц; парольная защита не поддерживается. DOCX проверяется как ограниченный ZIP/OOXML-контейнер. JSON-создание пустой инструкции не публикуется браузерным прокси. Выбор инструкции открывает карточку с историей на всю ширину; новая редакция загружается отдельным действием в диалоге. «Назад к инструкциям» возвращает список.

Следующие оригиналы добавляются через «Добавить редакцию» в выбранной инструкции. Старые редакции не перезаписываются; «Скачать оригинал» возвращает сохранённые байты. Один и тот же файл внутри инструкции не создаёт ещё одну редакцию. Повторное название в том же департаменте с той же должностной ролью, включая отсутствие роли, отклоняется: нужно открыть существующую инструкцию.

Форма отправляет одноразовый `upload_id`. Повтор неизменённого запроса после потери ответа возвращает уже сохранённую редакцию и не дублирует запись или аудит. Изменение файла, даты или названия создаёт новый запрос. После отзыва права повторная загрузка также закрывается.

Сохранение оригинала не утверждает актуальность документа и не выполняет смысловую сверку. Пока доступ Nova не настроен и ядро сверки не реализовано, AI-результаты не показываются. Сканы/OCR, извлечение функций, комплектность применимых ролей и утверждение остаются этапами общего roadmap.

## Проверки разработки

Создайте отдельную тестовую PostgreSQL, не используйте рабочую базу. Пример локального одноразового контейнера:

```sh
docker run --rm --name processhub-knowledge-test -e POSTGRES_PASSWORD=knowledge-test-only -e POSTGRES_DB=knowledge_test -p 127.0.0.1:55433:5432 postgres:17-alpine
```

В другом терминале из корня репозитория, с установленными `knowledge/requirements.txt`:

```sh
PYTHONPATH=knowledge python -m pytest knowledge/tests -q
```

Тестовая база по умолчанию — этот локальный контейнер. `KNOWLEDGE_TEST_DATABASE_URL` задаёт другую **тестовую** базу. Тесты создают и удаляют только собственные случайные схемы.

Миграции первой итерации применяются транзакционно при старте; повторный запуск безопасен. Промышленный выпуск потребует отдельного миграционного пользователя и ограниченного runtime-пользователя. CLI `migrate` позволяет подготовить базу отдельно, но текущий startup ещё вызывает проверку миграций.

Текущая проверка: **75 тестов Knowledge и 55 относящихся тестов Hub прошли**. На отдельном тестовом экземпляре в браузере проверены загрузка DOCX без должностной роли, создание роли без папок, выбор двух папок, назначение и отзыв с журналом. Подтверждён конфликт двух администраторов: старая форма получает 409, а обновлённый список сохраняет добавленную третью папку. У читателя административные модули скрыты. 21 дополнительная HTTP-проверка подтвердила область ролей, ограничения прав и точные байты оригинала. Ещё 4 проверки после отзыва подтвердили пустой список папок и 404 для инструкций, истории и оригинала. TypeScript, ESLint изменённых файлов, Vite и производственная сборка прошли.

Рабочий Hub на `http://127.0.0.1:8080/` пересобран, health сервиса подтверждён. Контроль рабочей базы: 41 папка, 0 должностных ролей, 0 инструкций, 0 прямых назначений, 0 ролей доступа и 0 участников. `test1@sqb.uz` сохранил глобальное административное назначение; тестовые данные и дополнительные назначения в рабочую базу не добавлялись.

Основные исходники: [rbac_routes.py](knowledge_service/rbac_routes.py), [rbac_store.py](knowledge_service/rbac_store.py), [store.py](knowledge_service/store.py), [registry_routes.py](knowledge_service/registry_routes.py), [registry_store.py](knowledge_service/registry_store.py), [005_access_roles.sql](knowledge_service/migrations/005_access_roles.sql). Контракт браузера проверяется в [backend/app/routers/knowledge.py](../backend/app/routers/knowledge.py).

## Резервирование

База документов не входит в резервную копию базы процессов. Снимите отдельную копию и проверьте восстановление в изолированной базе до реального пилота:

```sh
docker compose exec -T knowledge-db pg_dump -U knowledge -Fc knowledge > knowledge-backup.dump
```

Не добавляйте дампы, оригиналы инструкций, ключи или `.env` в Git.
